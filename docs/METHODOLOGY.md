## 2. ความท้าทายของชุดข้อมูล

เราพบ 5 อย่าง และแต่ละอย่างมีวิธีรับมือที่ต่างกัน

### 2.1 ความไม่สมดุลรุนแรง (3,855 : 1)

| วิธีที่ลอง | ผลลัพธ์ |
|---|---|
| weighted cross-entropy | **แย่ลงมาก** (top-1 0.60) — §D ใน 02-EXPERIMENTS |
| balanced sampler | ไม่ช่วยอย่างมีนัย |
| logit adjustment (tau sweep) | ช่วย balanced acc เล็กน้อย รายงานไว้ แต่ไม่ได้ใช้ |
| **สังเคราะห์ข้อมูลเติมคลาสหาง** | **ได้ผล — แต่ต้องเติมพอดี ไม่ใช่เติมเยอะ** (§7.3) |

### 2.2 ตัวอักษรไทยที่หน้าตาคล้ายกันมาก

คู่ที่โมเดลสับสนจริง วัดจาก confusion matrix:
`า↔ๅ` (27+21 ครั้ง), `ั↔้` (10+4), `ช↔ซ`, `ด↔ต`, `ผ↔ฝ`

ดู [`reports/analysis/G4_r18_g2init_randaug_20/confused_pairs.md`](../reports/analysis/G4_r18_g2init_randaug_20/)

### 2.3 label ผิดในชุดข้อมูลต้นทาง

ตรวจแล้วพบจริง — ดู [`reports/03-DATA-AUDIT-2026-09-22.md`](../reports/03-DATA-AUDIT-2026-09-22.md)
มีการแก้ label 629 จุด + ลบ 175 ภาพ ([`scripts/make_split_v2.py`](../scripts/make_split_v2.py))
และรอบสองอีก 146 จุด (§M ใน 02-EXPERIMENTS)

**ภาพที่ยืนยันด้วยตา:** ใน notebook ส่วน Error Explorer จะเห็นว่าหลายภาพที่ "โมเดลทายผิด"
แท้จริงคือ **label ผิด** เช่นภาพที่ label ว่า `ย` แต่เป็นสี่เหลี่ยมทึบ

### 2.4 ภาพเล็กมาก

8.5 % ของภาพสูงไม่ถึง 12 px, 4.2 % ไม่ถึง 9 px
→ ห้าม resize แบบยืดผิดสัดส่วน ต้อง **pad เป็นสี่เหลี่ยมจัตุรัสก่อน** (§4)

### 2.5 ข้อมูลมาจากเอกสารไม่กี่ฉบับ

ภาพจากเอกสารเดียวกันมีลายมือ/ฟอนต์/คุณภาพสแกนเหมือนกัน → การสุ่มแบ่ง train/val ธรรมดาทำให้
**ภาพจากเอกสารเดียวกันอยู่ทั้งสองฝั่ง** ซึ่งทำให้ผลดูดีเกินจริง แก้ด้วย doc-disjoint split (§3.3)

## 3. การเตรียมข้อมูลและการแบ่งชุด

### 3.1 ขั้นตอนทำความสะอาด

| ขั้น | ทำอะไร | ผล |
|---|---|---|
| 1 | อ่านทุกไฟล์ ทำ md5 | 62,707 ภาพ |
| 2 | ตัดภาพซ้ำ (md5 ตรงกัน) | ลดลง |
| 3 | ตัดไฟล์ `Copy of *` | ลดลง |
| 4 | ตัดภาพที่ไม่มีหมึก | ลดลง |
| 5 | แก้ label ตามการตรวจสอบ | 629 + 146 จุด |
| | **เหลือใช้งาน** | **59,942** |

### 3.2 การแบ่ง 80 : 20 (ตามที่โจทย์กำหนด)

**แบ่งแบบ stratified** คือแบ่งแยกในแต่ละคลาส เพื่อให้สัดส่วนคลาสใน train และ val เหมือนกัน
ใช้ seed 42 คงที่ → ทำซ้ำได้

```
train 47,949 (80.0 %)  |  val 11,993 (20.0 %)
```
ไฟล์: [`data/splits/split_seed42_v2.csv`](../data/) คอลัมน์ `split`

### 3.3 การแบ่งชุดที่สอง — doc-disjoint (สิ่งที่เราเพิ่มเอง)

แบ่งตาม **เอกสารต้นทาง**: เอกสารทั้งฉบับอยู่ใน train หรือ val เท่านั้น ไม่คร่อมกัน (คอลัมน์ `doc_split`)

| | stratified 80:20 | doc-disjoint |
|---|---|---|
| หลักการแบ่ง | สุ่มรายภาพ | สุ่มรายเอกสาร |
| ภาพจากเอกสารเดียวกัน | อยู่ได้ทั้งสองฝั่ง | อยู่ฝั่งเดียว |
| วัดอะไร | จำภาพที่คล้ายของที่เคยเห็นได้ไหม | **อ่านเอกสารที่ไม่เคยเห็นได้ไหม** |
| ค่าของโมเดลเรา | 0.9902 | 0.9872 |

**ทำไมสำคัญ:** stratified ให้ตัวเลขสูงกว่าเสมอ เพราะมันง่ายกว่า เราจึง**ใช้ doc-disjoint เป็นเกณฑ์เลือกโมเดล**
และรายงาน stratified ตามที่โจทย์กำหนด ทั้งสองตัวอยู่ใน [`reports/experiments.csv`](../reports/experiments.csv)

> ⚠️ โมเดลที่เทรนบน split หนึ่ง **ห้าม**วัดบนอีก split เพราะสองชุดนี้ซ้อนทับกัน — บังคับไว้ในโค้ดแล้ว
> ([`scripts/eval_split.py`](../scripts/eval_split.py) เตือนเมื่อใช้ผิด)

## 4. Pipeline การประมวลผลภาพ

โค้ด: [`src/thaichar/transforms.py`](../src/thaichar/transforms.py) ·
[`src/thaichar/infer.py`](../src/thaichar/infer.py)

| ขั้น | ทำอะไร | ทำไม |
|---|---|---|
| 1 | แปลงเป็นเทาระดับเดียว | รองรับ input ทุกแบบ |
| 2 | **`_reframe`** — ลอกกรอบสีเดียวออก แล้วเติมขอบใหม่ | เพื่อให้ขั้น 4 อ่านขั้วสีถูก |
| 3 | **Otsu threshold** | ตัดเงา/ความสว่างไม่สม่ำเสมอทิ้ง |
| 4 | ตรวจขั้วสีจากขอบภาพ กลับให้หมึกเป็นสีเข้มบนขาว | ข้อมูลจริงมีทั้งสองขั้ว |
| 5 | crop ชิดหมึก | ตัดพื้นที่ว่างที่ไม่มีข้อมูล |
| 6 | **pad เป็นจัตุรัส** + margin | **ห้ามยืดผิดสัดส่วน** — ตัวอักษรไทยเปลี่ยนความหมาย |
| 7 | resize → 64 × 64 | ขนาดที่เลือกจากการทดลอง (§5.2) |
| 8 | เข้ารหัส 3 ช่อง (`gray3`) | ให้เข้ากับ backbone ที่ pretrain บน ImageNet |
| 9 | ฟีเจอร์เรขาคณิต 4 ค่า (สูง กว้าง สัดส่วน ความหนาแน่นหมึก) | คืนข้อมูลขนาดที่ขั้น 6–7 ทำหายไป |

### 4.1 บทเรียนสำคัญ — บั๊กที่เจอตอนตรวจสอบระบบ

ขั้นที่ 2 เคยเติมขอบด้วย **ค่ากลางของสี 4 มุม** ซึ่งผิดเมื่อเส้นตัวอักษรแตะมุม (มุมเป็นสีหมึก)
ทำให้ Otsu อ่านว่าขอบคือพื้นหลัง แล้ว**กลับขั้วภาพทั้งใบ**

| | เส้นทางตอน validate | เส้นทางตอนใช้งานจริง |
|---|---|---|
| ก่อนแก้ | 0.9898 | **0.9695** (ผิด 10 ภาพ ถูก 0) |
| หลังแก้ (ใช้มุมที่สว่างที่สุด) | 0.9898 | **0.9898** |

รายละเอียด: [§N.0 ใน 02-EXPERIMENTS](../reports/02-EXPERIMENTS.md)

**สรุปง่ายๆ:** โค้ดที่ใช้ตอนวัดผลกับตอนใช้งานจริงต้องให้ผลตรงกัน ถ้าไม่ตรวจ จะไม่มีวันรู้

## 5. สถาปัตยกรรม CNN

โค้ด: [`src/thaichar/models.py`](../src/thaichar/models.py) (ใช้ `timm` เป็น backbone)

### 5.1 โครงสร้างที่ใช้

```
ภาพ 64×64×3
   │
   ├─ ResNet-18 backbone (11.2M params, pretrain จาก ImageNet)
   │     conv7×7 → maxpool → 4 stage ของ residual block → global average pool
   │     └─ ได้เวกเตอร์ 512 มิติ
   │
   ├─ ฟีเจอร์เรขาคณิต 4 ค่า ─┐
   │                          │
   └──────── concat 516 ──────┴─→ Linear → 72 คลาส
```

**จุดเด่นของ ResNet ที่ตรงกับงานนี้:** *skip connection* (`x + F(x)`) ทำให้ gradient
ไหลย้อนกลับได้โดยไม่จางหาย เทรนโครงข่ายลึกได้จริง ซึ่งจำเป็นเพราะตัวอักษรไทยหลายคู่
ต่างกันแค่รายละเอียดเล็กๆ (หัวกลม/ขมวด/หาง) ต้องใช้ชั้นลึกจับลักษณะระดับสูง

### 5.2 ทำไมเลือก ResNet-18 ที่ 64 px

เราทดลองจริง ไม่ได้เลือกลอยๆ ([§S และ §J ใน 02-EXPERIMENTS](../reports/02-EXPERIMENTS.md)):

| backbone | params | top-1 | latency CPU | หมายเหตุ |
|---|---:|---:|---:|---|
| **resnet18** | **11.2 M** | **0.9902** | **5.6 ms** | **เลือกตัวนี้** |
| efficientnet_b0 | 4.1 M | 0.9901 | 6.4 ms | เท่ากัน แต่เทรนช้ากว่า 2.5× |
| convnext_tiny | 27.9 M | 0.9898 | – | ใหญ่กว่า 2.5× ไม่ได้ดีขึ้น |
| mobilenetv3_small | 1.6 M | 0.9900 | 3.4 ms | เล็กสุด ส่งมอบเป็นทางเลือก |

**ข้อสรุป: ที่ 64 px กับตัวอักษรไบนารี backbone แทบไม่สำคัญ — สูตรการเทรนสำคัญกว่า**

ขนาดภาพ: 32 px → เสียความละเอียดของวรรณยุกต์, 96/128 px → ไม่ดีขึ้นแต่ช้ากว่า → **64 px คุ้มสุด**

## 6. Transfer Learning

**เราใช้ transfer learning สองชั้นซ้อนกัน** ซึ่งเป็นจุดที่ทำให้โมเดลเราต่างจากการทำตามปกติ

```
ImageNet (1.2M ภาพธรรมชาติ)
     │  ชั้นที่ 1 — ถ่ายโอนลักษณะทั่วไป: ขอบ มุม เส้นโค้ง
     ▼
Stage-1: ตัวอักษรไทยสังเคราะห์ 126,114 ภาพ จาก 203 ฟอนต์
     │  ชั้นที่ 2 — ถ่ายโอนความรู้เฉพาะทาง: "ตัวอักษรไทยหน้าตาแบบไหน"
     ▼
Stage-2: ข้อมูลจริง 47,949 ภาพ  →  โมเดลที่ส่งมอบ
```

config: [`configs/gen/G2_synth203du_pretrain_r18_64.yaml`](../configs/gen/) (stage-1) →
[`configs/final.yaml`](../configs/final.yaml) (stage-2)
น้ำหนัก stage-1 ที่ packaged ไว้: `weights/thaichar72_r18_synth203du_pretrain_init.pt`

### 6.1 หลักฐานว่าชั้นที่สองมีผลจริง

Stage-1 เทรนด้วย**ข้อมูลสังเคราะห์ล้วน ไม่เคยเห็นภาพจริงเลย** แล้ววัดบนภาพจริง:

| stage-1 ใช้ข้อมูล | top-1 บนภาพจริง | balanced |
|---|---:|---:|
| 72k ภาพ จาก 203 ฟอนต์ | 0.9395 | 0.9276 |
| **+ dataUpdate (126k)** | 0.9396 | **0.9354** |

**94 % โดยไม่เคยเห็นภาพจริงสักภาพ** — พิสูจน์ว่าความรู้ถ่ายโอนได้จริง

### 6.2 เทียบ 4 ทางเลือกของการ pretrain

| stage-1 | strat val | doc val | ฟอนต์ที่ไม่เคยเห็น |
|---|---:|---:|---:|
| ImageNet อย่างเดียว | 0.9902 | 0.9856 | – |
| + ฟอนต์สังเคราะห์ 26 แบบ (สูตรเดิม) | 0.9902 | 0.9856 | 0.834 |
| + ฟอนต์สังเคราะห์ 203 แบบ | 0.9901 | 0.9869 | – |
| **+ 203 ฟอนต์ + dataUpdate** | 0.9902 | **0.9872** | **0.868** |

**สรุปง่ายๆ:** บน val ธรรมดาทุกแบบเท่ากันหมด (อิ่มตัวแล้ว) แต่บนตัวชี้วัดที่วัดการ generalize จริง
(doc split, ฟอนต์ที่ไม่เคยเห็น) การ pretrain ที่ดีกว่าชนะชัดเจน

## 7. Data Augmentation

เราใช้ 2 ระดับ: **สังเคราะห์ข้อมูลใหม่ทั้งภาพ** (§7.1) และ **แปลงภาพระหว่างเทรน** (§7.2)

### 7.1 สังเคราะห์ตัวอักษรจากฟอนต์

### 7.2 การแปลงภาพระหว่างเทรน

โค้ด: [`src/thaichar/augment.py`](../src/thaichar/augment.py) — เรียกด้วย `aug:` ใน config

| op | ทำอะไร | ช่วงค่า |
|---|---|---|
| `affine` | หมุน เฉือน ย่อขยาย เลื่อน | หมุน ≤ 8° |
| `margin` | สุ่มขอบรอบตัวอักษร | ≤ 15 % |
| `stroke` | ขยาย/กัดเส้น | kernel 3×3 |
| `res_jitter` | ย่อความละเอียดแล้วขยายกลับ | ลงถึง 0.5× |
| `elastic` | บิดยืดหยุ่น | – |
| `speckle` | จุด noise | ≤ 3 % |
| `blur` | เบลอ | σ ≤ 0.6 |
| `erasing` | ลบบางส่วนทิ้ง | ≤ 20 % |
| `rebinarize` | binarize ซ้ำ | – |

สูตรที่ใช้คือ **`randaug`** — สุ่มหยิบ 2 op จากรายการข้างบน ด้วยความแรงสุ่ม

> 🚫 **ห้าม flip ทุกกรณี** — ตัวอักษรไทยไม่สมมาตร การพลิกสร้างตัวอักษรอีกตัวขึ้นมา
> เรา**วัดแล้ว**: พลิกแนวตั้งทำให้ บ↔ภ และ ย↔ถ สลับกันพอดี (§11.3)

### 7.3 เปรียบเทียบสูตร augmentation

เทียบแบบ **เงื่อนไขเดียวกันทุกอย่าง** — 20 epochs, resnet18, init เดียวกัน, ต่างแค่ `aug`
(F17/F14/F16/F18/F19 ใน [`reports/experiments.csv`](../reports/experiments.csv)):

| `aug` | top-1 | balanced | macro-F1 | **ความทนทาน** |
|---|---:|---:|---:|---:|
| `none` | 0.9804 | 0.9825 | 0.9804 | – |
| `trivial` | **0.9855** | 0.9829 | 0.9817 | 0.8931 |
| `morph` | 0.9820 | **0.9856** | **0.9830** | 0.8500 |
| `full` | 0.9802 | 0.9843 | 0.9812 | **0.9063** |
| **`randaug`** ← เลือก | 0.9839 | 0.9827 | 0.9791 | 0.9045 |

**สรุปง่ายๆ — และเป็นข้อสรุปที่น่าสนใจที่สุดข้อหนึ่งของโครงงาน:**
บน validation ธรรมดา **augmentation แทบไม่ช่วยเลย** (ต่างกันไม่ถึง 0.5 จุด และ `none` ก็ไม่ได้แย่)
แต่บน**ความทนทาน** มันต่างกันถึง **5.6 จุด** (0.8500 → 0.9063)

`morph` ได้ balanced/macro-F1 สูงสุดแต่**ทนทานแย่ที่สุด** เพราะชุด op ของมันไม่มี noise เลย
→ ทน rotate/blur ดี แต่พังที่ salt-pepper (เหลือ 0.175)

เราเลือก `randaug` เพราะได้ทั้งความทนทานระดับสูง (0.9045) และ top-1 ดี โดยไม่ต้องแลกอะไรมาก
เมื่อนำไปใช้กับ pretrain ที่ดีกว่า (§6) ได้ **top-1 0.9902 / ความทนทาน 0.9153**

> **ถ้าดูแต่ validation accuracy จะเลือก `trivial` ซึ่งทนทานน้อยกว่า 1.1 จุด**
> นี่คือเหตุผลที่เราตั้งเกณฑ์เลือกโมเดลแบบใน §9

### 7.4 เติมข้อมูลคลาสหาง — บทเรียนว่าเติมเยอะไม่ได้แปลว่าดี

| แบบ | คลาสที่เติม | ภาพที่เพิ่ม | สัดส่วนสังเคราะห์ | ความทนทาน | macro-F1 (doc) |
|---|---:|---:|---:|---:|---:|
| ไม่เติม (G4, ส่งมอบ) | 0 | 0 | 0 % | **0.9153** | **0.9798** |
| เติมทุกคลาสถึง 500 | 35 | 15,952 | มัธยฐาน **93.8 %** | 0.9041 | 0.9703 |
| เติมเฉพาะคลาส ≤ 20 ภาพ | 14 | 2,665 | – | 0.9136 | 0.9726 |

การเติมถึง 500 ทำให้ **ทั้ง 35 คลาสกลายเป็นข้อมูลสังเคราะห์เกิน 75 %** เช่น ตัว `ุ` มีของจริง 124 ภาพ

**สรุปง่ายๆ: ข้อมูลสังเคราะห์เหมาะใช้ pretrain มากกว่าเอามาผสมตอน fine-tune**

## 12. แนวคิดที่น่าสนใจ

### 12.1 ชุดทดสอบความทนทาน 3 กลุ่ม ที่ให้คะแนนคนละแบบ

จุดที่ต่าง: **เรายอมรับว่าบาง input ไม่มีคำตอบถูก และไม่รายงาน accuracy กับมัน**
แทนที่จะบังคับให้ทุกอย่างเป็นตัวเลข accuracy เดียว

### 12.2 Rotation search — แก้จุดอ่อนที่ inference โดยไม่ต้องเทรนใหม่

**แนวคิด:** โมเดลเทรนบนตัวอักษรตั้งตรง ดังนั้น "มุมที่โมเดลมั่นใจที่สุด" คือสัญญาณว่าภาพตั้งตรงแล้ว
→ หมุนภาพไปทีละมุมแล้วเลือกคำตอบที่มั่นใจสุด

ถ้าทำกับทุกภาพจะ**ขาดทุน** เราจึงใส่การ์ด 2 ชั้นที่**จูนจากการวัด**:
- ค้นเฉพาะภาพที่อ่านตั้งตรงแล้วไม่มั่นใจ (เข้าเงื่อนไขแค่ 3 % ของภาพปกติ)
- ยอมเปลี่ยนคำตอบเมื่อมุมใหม่ชนะเกิน 0.30

| | ไม่มีการ์ด | **มีการ์ด** |
|---|---:|---:|
| clean | −1.4 จุด | **±0.0 จุด** |
| หมุน 30° | +44 จุด | **+37.7 จุด** |
| หมุน 45° | +77 จุด | **+75.1 จุด** |

ทดสอบกับไฟล์จริง: โฟลเดอร์หมุน 35° ได้ **0.2429 → 0.8286**
โค้ด: `predict_with_rotation_search` ใน [`src/thaichar/infer.py`](../src/thaichar/infer.py)

### 12.3 การตรวจจับว่าข้อมูลหมุนหรือไม่ โดยไม่ต้องมี label

**ปัญหาที่ไม่ตรงไปตรงมา:** ความมั่นใจสูงขึ้นเวลาหมุน**กับภาพเสียทุกแบบ** ไม่ใช่เฉพาะภาพหมุน
(ภาพความละเอียดต่ำ lift 0.22, เส้นบาง 0.23 ทั้งที่ไม่ได้หมุนเลย) ใช้ lift อย่างเดียวเตือนผิด 3 จาก 5 ชุด

**ตัวแยกที่ถูกต้อง: มุมที่ชนะต้องสอดคล้องกันทั้งชุด** เพราะกระดาษทั้งแผ่นหมุนไปเท่ากัน

| ชุดทดสอบ | lift | มุมที่เห็นตรงกัน | ตัดสิน |
|---|---:|---:|---|
| ตั้งตรง | 0.013 | – | ✅ ตั้งตรง |
| หมุน 35° | 0.519 | **90 %** | ✅ หมุน |
| ความละเอียดต่ำ | 0.216 | 46 % | ✅ เสียแต่ไม่หมุน |
| เส้นบาง | 0.226 | กระจาย | ✅ เสียแต่ไม่หมุน |

โค้ด: [`scripts/triage_input.py`](../scripts/triage_input.py)

### 12.4 Probe คลาสหางที่กันข้อมูลออกทั้งกลุ่ม

ชุดข้อมูลสังเคราะห์ที่ได้มาแบ่ง train/val ของตัวเองแบบ**รายภาพ** ทำให้ **99.2 %** ของฝั่ง val
ซ้ำต้นฉบับกับฝั่ง train เราตรวจเจอและแบ่งใหม่แบบ**กันทั้งตระกูลฟอนต์และทั้งลายมือ**

## 14. สิ่งที่เรายังวัดไม่ได้

**เราเลือกจะบอกตรงๆ แทนที่จะปิดบัง**

| ข้อจำกัด | ตัวเลข |
|---|---|
| คลาสที่ไม่มีภาพ validation เลย | **8 คลาส** (ฃ ฑ ฤ ฬ ฯ ฮ ๔ ๕) |
| 24 คลาสที่มีข้อมูล < 50 ภาพ มีภาพใน doc-val รวมกัน | **123 ภาพ** |
| ภาพเดียวพลิกในคลาสที่มี val 3 ภาพ = balanced accuracy ขยับ | **0.46 จุด** |

**ผลที่ตามมา:** ทุกข้อสรุปเรื่องคลาสหางถูกจำกัดด้วยเครื่องมือวัด ไม่ใช่ด้วยตัวโมเดล
เราทดสอบ 4 วิธีเติมข้อมูลคลาสหาง แต่**พิสูจน์ทางสถิติไม่ได้ว่าอันไหนดีกว่า** (p = 0.23)
จึงเลือกไม่เปลี่ยนตัวส่งมอบ แทนที่จะอ้างผลที่ยืนยันไม่ได้

**ทางแก้ที่ไม่ใช่งานโค้ด:** หาภาพจริงของ 35 ตัวอักษรที่ขาด มาเป็นชุดทดสอบ
